  ### ✅ AC2 — Anti-Flapping (Hysteresis + Cooldown)

  Test: Scale up → immediately try scale down

    # 1. Generate high CPU to trigger a scale-up
    kubectl port-forward svc/target-workload-service 8080:8080 -n workload-system &
    curl "http://localhost:8080/api/load/cpu?duration_ms=5000&concurrency=4"
    
    # 2. Watch replicas increase (wait ~15–30s)
    kubectl get deploy target-workload -n workload-system -w
    
    # 3. After scale-up, check status
    kubectl get aa target-workload-autoscaler -n workload-system \
      -o jsonpath='{.status.lastScaleAction} {.status.lastScaleUpTime}'
    # → SCALE_UP  <timestamp>
    
    # 4. Now remove load — reasoner will recommend scale-down
    # Wait 15s for next reconcile, observe that scale-down is REJECTED
    kubectl get aa target-workload-autoscaler -n workload-system \
      -o jsonpath='{.status.lastGuardrailAction} {.status.lastGuardrailReason}'
    # → REJECTED  scale-down within hysteresis window (10 min)

  ### ✅ AC3 — Reactive HPA Fallback on Reasoner Outage

  Test: Kill the reasoner pod, observe fallback

    # 1. Kill the reasoner
    kubectl scale deploy reasoner-service --replicas=0 -n workload-system
    
    # 2. Wait one reconcile cycle (~15s), then check status
    kubectl get aa target-workload-autoscaler -n workload-system \
      -o jsonpath='{.status.fallbackEngaged} {.status.conditions[?(@.type=="ReasonerHealthy")].status}'
    # → true  False
    
    # 3. Generate some CPU load — HPA fallback should still scale correctly
    make reasoner-port-forward
    curl "http://localhost:8080/api/load/cpu?duration_ms=3000&concurrency=2"
    kubectl get deploy target-workload -n workload-system -w
    
    # 4. Check event for fallback
    kubectl describe aa target-workload-autoscaler -n workload-system | grep -i "fallback\|outage"
    
    # 5. Restore reasoner
    kubectl scale deploy reasoner-service --replicas=1 -n workload-system
    # After next reconcile, ReasonerHealthy → True, fallbackEngaged → false
