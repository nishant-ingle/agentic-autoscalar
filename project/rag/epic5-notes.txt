  ## 1. What is "Operational Memory" and RAG in this Project?

  ### Why Plain Kubernetes HPA Fails

  Kubernetes' built-in Horizontal Pod Autoscaler (HPA) is purely reactive:
  1. When traffic surges → CPU spikes.
  2. HPA observes high CPU → HPA adds pod replicas.
  3. The pitfall: If high CPU or latency was caused by an overloaded database, memory leak, or connection pool exhaustion,
  adding 5 new replicas opens 5 new database connections—crashing PostgreSQL and bringing the entire system down.
  ### How RAG (Retrieval-Augmented Generation) Solves This
  Operational Memory gives our agentic autoscaler the experience of a seasoned Site Reliability Engineer (SRE):
  • Vector Embeddings: Human text (runbooks, post-mortems) is passed through a local ML model (all-MiniLM-L6-v2) that
  converts sentences into 384 floating-point numbers (a coordinate in semantic space).
  • Vector Database (pgvector): These embeddings are stored in PostgreSQL inside a VECTOR(384) column equipped with an HNSW
  (Hierarchical Navigable Small World) vector index.
  • Semantic Similarity Search (<=> operator): When the system observes an anomaly (e.g. "95% CPU, 2200ms latency, thread
  pool starvation"), it embeds that symptom and queries PostgreSQL using cosine distance.
  • Context Augmentation: PostgreSQL retrieves the top matching runbooks (e.g., "Flash Traffic Surge: scale up by 2.5x and
  hold for 5 minutes"). The reasoner receives this advice and makes an informed scaling recommendation.

  ### Detailed Breakdown of Every File
  #### 1. approach_syn_generator.py
  The primary execution engine:

  • load_config(path): Reads config.yaml, expands environment variable expressions like ${PGHOST:-localhost}, and enforces
  mode: synthetic.
  • get_db_connection(config): Connects to PostgreSQL using configured parameters or environment overrides (PGHOST, PGPORT,
  PGDATABASE, PGUSER, PGPASSWORD).
  • init_database(conn): Executes CREATE EXTENSION IF NOT EXISTS vector;, creates the rag_documents table with VECTOR(384),
  and creates an HNSW index using vector_cosine_ops (fixing the small-dataset issue with IVFFLAT).
  • load_incidents_from_yaml(path): Parses synthetic_epic5.yaml.
  • generate_embeddings(texts): Uses SentenceTransformer("all-MiniLM-L6-v2") to generate 384-dimensional dense vectors.
  • bulk_insert_documents(conn, docs): Uses psycopg2.extras.execute_values for high-performance single-roundtrip batch
  insertion.
  • search_similar_documents(conn, query_vec, limit): Queries rag_documents ordered by cosine distance (embedding <=>
  query_vec::vector) ASC LIMIT k.
  • run_pipeline(...): End-to-end orchestration callable both as a Python module (python -m epic5.approach_syn_generator) and
  programmatically by test harnesses.
  #### 2. config.yaml
  Defines runtime configurations:
  • mode: synthetic: Validated on startup.
  • database: Configured for your macOS Postgres (host: localhost, port: 5432, dbname: agentic_autoscalar_db, user:
  agentic_autoscalar, password: agentic_autoscalar).
  • embedding: Specifies model all-MiniLM-L6-v2 and dimension: 384.
  #### 3. synthetic_epic5.yaml
  Contains 5 production-grade SRE incident post-mortems and runbooks:
  1. INC-CPU-SPIKE-001: Flash traffic surge exhausting CPU (scale 2.5x immediately, 5m cooldown).
  2. INC-MEM-LEAK-002: Heap accumulation leading to OOMKills (temporary +2 scale and rolling restarts).
  3. INC-FLAP-OSC-003: Destructive metric flapping (enforces 10m hysteresis cooldown).
  4. INC-DEP-LATENCY-004: Downstream DB pool exhaustion (do not scale replicas, apply circuit breaker).
  5. INC-BATCH-BURST-005: Predictable scheduled cron burst (step scale 2 minutes before the hour).
  #### 4. test_approach_syn_generator.py

  7 automated unit and integration tests:

  1. test_load_config_valid: Asserts valid config loads properly.
  2. test_load_config_invalid_mode: Asserts rejection of unsupported modes.
  3. test_load_incidents_from_yaml: Validates YAML parsing and schema completeness.
  4. test_init_database_and_vector_table: Validates pgvector table creation.
  5. test_generate_embeddings_dimension: Validates vector dimension is exactly 384.
  6. test_bulk_insert_and_similarity_retrieval: Inserts distinct incident vectors and asserts cosine similarity queries
  return the semantically matching runbook.
  7. test_run_pipeline_end_to_end: Tests full ingestion pipeline.
  #### 5. epic5-approach-syn-job.yaml

  A Kubernetes manifest containing:

  • ConfigMap (epic5-synthetic-schema): Injects config.yaml and synthetic_epic5.yaml directly into pods.
  • Job (epic5-approach-syn-job): Runs python -m epic5.approach_syn_generator, points PGHOST to the cluster postgres service,
  mounts the ConfigMap at /etc/epic5, and exits with code 0 once data is seeded.

  #### 6. Dockerfile
  Builds the standalone image. It pre-downloads the embedding weights during docker build, ensuring the container starts
  instantly in cluster environments without internet dependencies.

  ### 2. How Can We Trust that the Synthetic Data is of Good Quality?
  Evaluating synthetic data quality for operational RAG is done along three dimensions:

  1. Deterministic Semantic Separability (Cosine Distance Thresholds):
      • High-quality data has high clustering separation: an inquiry about "CPU thread starvation" should match the CPU
      incident with a low distance (≈ 0.35 - 0.45), while showing distance > 0.70 against an unrelated issue like "Postgres
      connection leak".
      • This is verified in our test suite test_approach_syn_generator.py, which asserts query-retrieval fidelity.
  2. Schema Invariance:
      • Synthetic incidents must mirror real-world SRE post-mortems: Symptom → Root Cause → Explicit Remediation →
      Guardrail/Constraint.
      • Each entry in synthetic_epic5.yaml contains these exact four components so the reasoner receives actionable context.
  3. Ground-Truth Benchmark in Epic 7:
      • In Epic 7, we test the autoscaler with Locust load tests under flash traffic. If synthetic runbooks guide the agent
      to scale quickly during bursts and reject flapping, p99 latency and SLA violations drop compared to standard HPA. That
      empirical test is the definitive benchmark of data quality.

### 2. Ensuring Synthetic SRE Runbooks Match Prometheus & MCP Metrics

  Yes, the synthetic runbooks and incoming telemetry are systematically aligned:

  1. Shared Symptom Metric Vocabulary:
  The synthetic incident generator (synthetic_epic5.yaml) embeds incidents structured around the exact dimensions Prometheus
  measures:
      • CPU utilization percentages (e.g. 25% to 92%)
      • P99 latency thresholds (e.g. >1800ms, 3200ms)
      • Throughput (RPS) and Error rates
  2. Standardized Query Embedding Format (graph.py:49-54):
  When live metrics arrive from Prometheus/MCP, the retriever creates a structured query string matching that exact
  vocabulary:
    query_str = (
        f"Workload: {payload.workload_name}. CPU: {payload.cpu_utilization_percent:.1f}%, "
        f"P99 latency: {payload.http_p99_latency_ms:.1f}ms, Error rate: {payload.error_rate_percent:.1f}%, "
        f"Throughput: {payload.http_requests_per_second:.1f} RPS."
    )

  3. Symmetric Embedding Space:
  Both the runbook documents and runtime queries use the identical embedding model (all-MiniLM-L6-v2, 384 dimensions). Dense
  vector cosine similarity (<=>) matches live telemetry spikes to the most relevant historical incident even if exact
  phrasing varies slightly.
